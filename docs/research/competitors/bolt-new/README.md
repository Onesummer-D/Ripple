## 01. 研究动机、问题与边界

Ripple 希望解决的并不是“让 AI 修改网页文案”本身，而是：当用户维护已有数字作品时，一次修改可能牵动共享组件、多个页面、设备布局、图片裁切和隐含的业务语义；用户想知道**哪里可能变、哪里真的变、哪里尚未核实、能否只改一部分**。竞品调研要先了解成熟 Agent 已能完成多少，再判断剩下的真实摩擦在哪。

本轮围绕四组问题：①接入作品与生成作品的成本；②在普通编辑、共享修改与局部修改下，影响关系何时被说明、如何被呈现；③构建、搜索、浏览器检查、多视口与版本恢复到底提供何种证据；④Ripple 能借鉴哪些交互与工程方案，以及哪些“优势”仍是待验证假设。

**已测试**：新建四页站点；可视化点选编辑；跨页共享导航修改；首页局部覆盖；全站季节活动更名；多设备预览；版本历史的预览/退出；明确要求“先分析、不修改”的商品角标局部覆盖（最终 V6）；公开发布与编辑器版本区分。  
**未测试**：通过 GitHub 导入 `Onesummer-D/NCDA` 已有项目、GitHub 双向同步、代码导出与授权全流程、多人协作、不同定价层级、自动浏览器截图 API、长期使用成本、完整 Git Diff、可复现的端到端耗时与点击数。  
**未作结论**：Bolt 内部是否使用隔离工作区、AST、自动视觉回归等具体实现；其他功能入口或高阶模式是否提供截图/影响图；所有平台和所有项目是否都能重现本轮结果。

## 03. 逐项实验记录（原始实测）

### 实验 B01｜画布直接改 Hero 标题：可视化编辑与保存机制

**任务**：将首页 Hero 标题「山野之间，器以载道」改为「山野之间，器以新生」。  
**步骤**：进入 Preview → 开启 Select → 点中 Heading → 直接在画布修改 → `Add changes` → 左侧显示 `1 visual change` → `Save changes` → Bolt 读取并编辑 `src/pages/HomePage.tsx`、报告 `Built to verify the change` → 生成 V2 → 后续发布使公开网页更新。

**结果**：画布在输入时立即显示新文案，但当时**不代表 React 源码已落盘，也不代表已发布网站更新**。`Add changes` 是将编辑操作加入待保存批次；`1 visual change` 在此表示累计的一项可视化编辑记录，**不是**“只改变了一个 DOM 元素”“已完成全站检测”或“检测到一处布局风险”。点击 `Save changes` 后，才进入 Agent 处理源码阶段。研究者确认 V2 版本形成，后续公开网站也出现更新。

![E04：画布可视化编辑标题](assets/E04.png)

![E05：1 visual change 与 Save changes 队列](assets/E05.png)

**界面摩擦（O）**：Select 点选不总是灵敏；有时光标表现为文本插入竖线，有时为手形/可选区域；修改导航名称时，实际需要准确点到四个字而不是整块 Navigation 容器。这个问题可以作为 Ripple 选择命中区域、悬停高亮、祖先组件与文字节点切换设计的参照。**不能推断它对所有页面都这样。**

**Ripple 的机会（H）**：保留就地可视编辑的直接性，但在 `Add changes` 或真正应用之前，默认展示“该内容对应的来源和可能影响节点”；将视觉编辑数量、关联实例数量、异常数量分开展示，避免用户误把 `1 visual change` 当作影响规模。

### 实验 B02｜共享导航品牌名称：四页同步

**任务**：把导航栏的品牌名「山野器物」改成「山野手作」。  
**观察**：研究者在导航栏直接选择文字并提交后，Bolt 修改共享 `src/components/Navigation.tsx`，四页导航自然同步为「山野手作」。界面在执行后给出了 Read、Edited、Built 三种操作记录，指出改动发生在共享组件。此前普通编辑流程中未看到一次默认的跨页影响图、逐页预演或要求用户先选范围的交互。

**关键区分**：共享组件同步不是 Bolt 错误；对“全站统一改品牌”的请求，这通常是合理行为。风险来自用户可能只想改首页却不知道共享关系。因此本实验不应描述成“Bolt 误改四页”。

### 实验 B03｜明确要求仅首页修改：Bolt 成功实施局部 Scope

**任务**：其他三页品牌名仍为「山野手作」，仅首页显示「山野工坊」。  
**执行前**：Bolt 明确识别 Navigation 是四页共享组件，提出依据当前页面动态呈现品牌名的技术方案；这属于**修改前方案解释（已确认）**，但没有在用户提交修改前直接呈现四页的视觉方案对照或基于关系图的范围勾选。  
**执行后**：用户逐页确认：首页「山野工坊」，秋季活动、商品专题、品牌故事三页「山野手作」；记录显示仅读写 `src/components/Navigation.tsx`，完成构建，创建 V4。研究者随后贴出的真实源码中出现以下表达式：

```tsx
{currentPage === 'home' ? '山野工坊' : '山野手作'}
```

**证据层级**：源码表达式（C）+ 用户逐页确认（M）+ Bolt 构建报告（A）；“Bolt 解释了方案”成立，“Bolt 先自动生成四页差异截图”没有本轮证据。点开行动旁的 Open 显示的 Details 为操作摘要，并非直接打开逐行代码 Diff 或真实视觉证明；用户仍可进入 Code 模式自行检查。

![E10：局部 Scope 修改过程](assets/E10.png)

**Ripple 的机会（H）**：普通 Agent 已可通过条件表达式完成局部覆盖，因此仅提供“仅当前页面”按钮不足以构成壁垒。Ripple 应在用户**尚未知道共享关系、尚未明确范围**时主动提示“一个共享来源、四个页面消费”，让其在“仅当前实例 / 全部共享实例”等备选方案间比较效果和代价，并说明这种特殊分支是否会成为维护负担。

### 实验 B04｜自然语言更新整场秋季活动：语义检索与多文件修改

**任务**：把网站本季秋季活动更名为「秋日手作节」，更新本次活动相关名称与宣传文案，保持品牌故事、独立商品信息及其他无关内容不变。**提示词有意不告知具体页面、文件、共享关系和验证方法。**

**Bolt 的实际行为**：先搜索「秋日新品」「山野秋收」「秋季活动」「秋收」等关键词，形成编辑计划，然后报告修改六个文件：

1. `src/components/Navigation.tsx`：活动导航名称；
2. `src/components/Footer.tsx`：页脚链接标签；
3. `src/components/ProductCard.tsx`：商品角标文案；
4. `src/pages/HomePage.tsx`：首页的活动标识、Hero 和宣传文字；
5. `src/pages/AutumnPage.tsx`：活动页名称、介绍、权益与商品标识；
6. `src/pages/ProductsPage.tsx`：商品专题的相关活动名称。

Bolt 报告构建通过、执行文本搜索确认旧名称在业务相关位置被替换；而品牌故事页的两处「秋日新品」属于历史时间线语境，按提示保持。用户随后在实际页面与多个视口核对，截图中可以看到「秋日手作节」展示以及品牌故事不应修改的内容仍在。

![E12：六文件更新计划](assets/E12.png)

![E14：六个文件的修改结果说明](assets/E14.png)

**最关键的发现**：这个案例证明成熟 Agent 不仅懂代码共享，还能一定程度上理解业务语义，识别同一活动的不同写法并避免明显历史语境误改。然而我们当时看到的详细范围说明主要发生在**修改完成之后**；未观察到普通流程中默认的“用户先选具体关联位置 → 系统预演 → 再应用”的完整决策界面。  
**谨慎限定**：上述六个文件及历史保留是 Bolt 记录/截图支持的结果，但本报告没有独立比较完整 Git Diff；不能据此断言项目其他所有状态、业务功能和设备都无变化。

**两类关系必须区分**：

- **来源/结构关系**：例如 Navigation 被四页引用，或多个商品卡片取自相同源组件、Token、数据字段；AST、运行时定位与依赖追踪能给出较强工程证据。
- **业务/语义关系**：六处独立硬编码字符串可能都指同一场营销活动，也可能只是历史材料、独立商品描述或巧合同名。AST 本身不能理解“这段属于本季宣传，那段属于往年历史”，需要语义检索、AI 候选判断、用户确认及浏览器验证；未知关系应标成未知。

**对 Ripple 的启发（H）**：不应把“同名即共享”当作强确定关系；设计“结构共享（已证实）/语义相关（候选）/历史引用（建议排除）/无法判定（未知）”等清楚标签，并将生成的候选范围交由用户选择验证。

### 实验 B05｜多设备预览、断点与正常变化

**操作**：使用预览工具栏的设备菜单，检查 iPhone/SE、Galaxy、iPad Mini、iPad Air、iPad 13 英寸及桌面视口；研究者专门检查了 375px 附近的手机端、约 744px / 820px 的平板，以及 1024px 和更宽的桌面布局。Bolt 提供多种设备预设与预览缩放。研究者还尝试 Custom 模式，但当时没有成功直接编辑宽高参数，后改用相近的 iPad Mini 预设。不同的 UI 缩放百分比（例如 80%、90%）**不是网页 CSS 视口宽度**，应区分。

**实测现象**：小视口下，顶部四项导航自然收拢为汉堡菜单；宽视口可完整展示四项。这是正常响应式布局，不是“样式发生变化就一定有风险”。已查看的截图未发现明确的标题/按钮重叠或溢出；但只是有限视口、有限页面与有限滚动位置的人工抽样，不能推定所有断点均正常。

![E15：设备预设菜单](assets/E15.png)

![E16：小视口商品卡片](assets/E16.png)

![E18：较宽视口可见完整导航](assets/E18.png)

**对 Ripple 的直接设计要求（H）**：保留 1440 / 768 / 375 三视口联动是合理的比赛演示主线，但要检测并分类：文本正常换行、栅格正常折叠、图片合理裁切 = 预期变化；内容遮挡、点击目标不可达、越界、无法滚动、关键组件丢失 = 需关注异常。检测必须有基线和页面语义，不能把 DOM 坐标变化一律标红。允许用户快速聚焦有差异的视口，而非先手工选很多设备再逐一滚动查找。

### 实验 B06｜版本历史：预览、恢复与文本证据错位

**操作**：查看版本历史，观察到创建网站的 V1、Hero 修改 V2、共享品牌改名 V3、首页局部覆盖 V4、全站秋季活动更名 V5，最终角标局部覆盖 V6。界面提供版本标题、时间、搜索、Bookmark、点击预览、`Exit preview` 与 `Restore this version`。研究者预览了 V4，再退出预览，恢复到 V5 的当前工作状态；没有实际执行覆盖性恢复操作，因此**“Restore 按钮存在”已确认，“点击 Restore 后恢复的所有副作用”未实测**。

![E19：版本历史列表](assets/E19.png)

![E20：进入旧版的只读预览并显示恢复按钮](assets/E20.png)

**值得借鉴**：过去版本可直接交互预览，降低回滚心理成本；编辑与公开部署的版本状态应分开呈现。`Bookmark` 是为版本加书签，不是实际执行恢复。

**值得改进的细节**：在本轮旧版预览的某些界面，左侧仍可看到当前较新任务的 Agent 修改说明，右侧展示较旧版本的网页；研究者容易误以为两者对应同一次修改。这不意味着 Bolt 版本恢复错误，而提示 Ripple 可以让“版本胶片—当版页面—当版证据—版本之间变化区域”同步切换。尚未观察到一个默认的界面直接回答“从 V4 到 V5，哪几个视觉区域变了”；这并不代表 Bolt 在任何入口都不支持对照。

### 实验 B07｜先分析后执行：只让「素白陶碗」恢复旧角标

**背景**：V5 更名之后，`ProductCard.tsx` 共享商品角标显示「秋日手作节」，若直接改回「秋日新品」，可能使其他 `isNew` 商品同步回退。目标是仅恢复商品 `p001`（素白陶碗）的角标，其他商品及页面保留新活动命名。

**第一阶段（明确要求不得修改）**：提示 Bolt 阅读代码、查找共享组件与商品数据，先给出影响预测、预计改动文件、错误扩散风险和验证计划，等待人工确认。Bolt 读取 `src/components/ProductCard.tsx` 和 `src/data/products.ts`，检查活动页面还有独立的内联角标逻辑，说明 `p001`、`p004`、`p007` 等 `isNew` 商品受共享卡片文案影响。它指出：简单全局替换会误伤首页及商品专题中其他商品，提出只在 `product.id === 'p001'` 时显示旧角标，其余保留新文本。**这是本轮最强的“修改前主动分析”证据，但它是被明确提示触发的，不是对默认流程的证明。**

## 05. 易误判之处：本次结论必须写得准确

1. **`1 visual change` ≠ 一个受影响位置，也 ≠ 已验证全站。** 它对应这次加入保存队列的一项画布编辑操作。真正修改文件、页面实例和样式区域可能更多。
2. **`Built to verify` ≠ 浏览器视觉回归通过。** 只能记录为平台报告构建通过；代码搜索有助核查文本，不足以证明无溢出、遮挡或功能故障。
3. **共享组件改动不是天然错误。** 用户希望全站改名时，四页同步正是正确行为；只改首页才需要局部 Scope。
4. **Bolt 能做修改前分析。** V4 有先解释技术方案；V6 能读代码、预测误伤并等待确认。准确表述是“普通流程中没有观察到默认的结构化可视影响预告”，不能说“Agent 根本做不到先分析”。
5. **多终端预览是真实存在的竞品能力。** Ripple 的价值不能写成“首创手机预览”；应体现在候选变更与基线之间的自动、多视口、有证据的比较。
6. **正常响应式变化不应列为风险。** 导航收折与标题换行本身是预期布局；只提示异常变化、来源不明或未验证。
7. **人工点击与自动验证是两回事。** 用户已核对 V6 的目标商品，但不能说 Bolt Agent 自动完成了全站三视口截图测试。
8. **`Restore this version` 按钮存在 ≠ 已亲自回滚成功。** 本次只操作了旧版预览和退出，未做真正 Restore 的副作用测试。
9. **可见操作日志不是全部内部机制。** 未看到 worktree/sandbox/AST/Playwright 日志，不能反向断言 Bolt 没有任何内部隔离或额外测试。
10. **局部源码条件表达式解决当前需求，不自动证明长期架构最优。** 是否引入管理型 ScopeDecision，需要真实多次覆盖需求支持。

## 06. Ripple 的价值主张：从工具链罗列到产品体验，同时保留技术亮点

**值得竞赛展示的技术融合创新**：来源依赖的 AST/ts-morph 分析、运行时 DOM→组件/数据追踪、首次完整构图与增量更新、关系图缓存与变更失效、语义检索辅助候选、草稿注入、隔离 Worktree 候选补丁、Playwright 三视口截图、DOM 几何和 computed style 检测、视觉差异、Evidence 证据溯源、结果状态分级、范围决策、版本回滚。使用成熟工具并把它们组合成低成本、易操作的闭环本来就有技术价值；关键是讲清**各自解决哪一个问题、怎样协同、实际节省了什么、测试范围在哪里**，而非单纯宣称技术数量多就是更强。

研究假设 H1：普通用户更容易从“网页位置 + 影响范围 + 可切换视口 + 证据”理解复杂改动，而不需要阅读 Agent 的 Read → Edited → Built 日志。  
研究假设 H2：把对“受影响范围”的说明放在**原项目正式改动前**，可以减少误修改、重复沟通与恢复成本。  
研究假设 H3：当任务涉及跨页共享与不确定语义时，结构关系与语义候选的分级展示，比一次性由 Agent 全权处理更容易建立可控的编辑信任。  
研究假设 H4：采用轻量注入与完整隔离两条预演通路，有机会在保证验证真实性的前提下优化等待时间与算力成本。

**这些全部是待用对照实验检验的假设，而不是本轮 Bolt 实验已经证明 Ripple 更快、更安全或更便宜。**

### 概念用户旅程：明确区分三个时间点

```text
首次接入项目
  └─ 静态 AST / 依赖分析 + Runtime 来源关联 → 构建并缓存关系图
用户在网页选中内容，输入候选修改（原项目不变）
  └─ 潜在影响预告：结构共享实例 + 语义候选 + 未知来源 + 初步 Scope
  └─ 用户比较：仅当前位置 / 更新本次活动 / 全部同源位置
隔离候选预演（仍未正式应用）
  ├─ 快速通路：注入候选文本、媒体、样式 token
  └─ 完整通路：在独立 Worktree 修改并编译运行
Playwright 实际验证
  └─ 1440 / 768 / 375 截图 + DOM 几何 + computed style + 视觉差异 + Evidence
用户查看涟漪并调整范围
  └─ 确认差异、正常变化、待核实与错误；必要时重新预演
确认应用
  └─ 检查源码基线 → 应用经过验证的同一份补丁 → 验证状态与版本记录
（部署上线为后续独立步骤，不应与应用混为一谈）
```

上面“潜在影响预告”来自**已知关系**，可在实际修改候选之前提供；“真实视觉结果”则必须先在**隔离环境中实际运行过候选修改**才能可信呈现。不能宣称不渲染、不改动任何环境，就可以知道复杂视觉变化。Ripple 的关键是“不提前污染正式项目”，不是“不允许在任何地方修改代码”。

### 两条预演路径的工程边界

| 路径 | 做法 | 较适合 | 主要风险与验收 |
|---|---|---|---|
| A｜草稿注入 | 保持原站点运行，将候选文案、图片、颜色/样式临时注入预览 | 简单文案、媒体替换、CSS Token | 可能绕过条件逻辑/构建状态；最终应用必须验证与草稿等效 |
| B｜隔离 Worktree | 创建干净的独立工作副本，在隔离环境应用代码补丁，编译后由真实浏览器检查 | 共享组件、复杂布局、逻辑、跨文件改动、外部仓库 | 启动成本与依赖更高；必须限制执行环境并记录依赖/基线 |

**所见即将所得的一致性要求**：预演过的 Worktree 补丁应绑定**基线 Commit/文件指纹**；确认正式应用前检查基线没有漂移，然后应用同一个已验证补丁。禁止用户确认 A 后再次让 Agent 从自然语言重写出一个不一定等价的 B。如果基线变化则标记失效并重新验证。草稿注入也必须记录候选映射和最终落盘的一致性测试，不可只要求视觉暂时相似。

### 关系和结果状态：避免伪确定性

**关系层**：`STRUCTURAL_CONFIRMED`（可证实的源码/运行时共享）、`SEMANTIC_CANDIDATE`（AI/检索提示的业务关联）、`EXCLUDED_BY_CONTEXT`（历史等应排除候选）、`SOURCE_UNKNOWN`（来源未明），并分别携带来源文件、关联组件、页面实例与可信度/证据类型。上述字段为研究建议，**并非声称当前 B 引擎已经全部实现**。

**视觉/验证结果层**：确认异常、正常视觉变化、未见显著异常（仅限覆盖的测试）、来源未知、尚未验证；将“未知”和“未验证”与“安全”严格区别。例如：导航从四项变为汉堡菜单 = 正常响应式变化；标题或按钮被遮挡 = 已确认异常；只跑过 build 没跑浏览器 = 未验证，而非安全通过。

### 一个适合高质量叙事的交互演示（概念示例，不是已实现）

用户希望“将本季秋季活动统一改为「秋日手作节」”。Ripple 首先呈现一张网页上的涟漪：已确认使用同一数据/组件的区域直接连线；“活动文案”“促销卡片”作为语义相关候选；“品牌故事年份记录”建议排除并等待人工复核。用户选择“只更新本次活动关联内容”，进入三视口预演，看到正常换行与真正的按钮遮挡分别标记，再去除一处不想要的修改并重新验证；最后应用的是刚刚验证通过的同一候选补丁。**这套叙事目前属于目标体验，不得在比赛成果中误写为已交付。**

## 08. 对 Ripple 已规划技术任务的直接启发

以下是研究后建议验收的问题，不意味着擅自修改既定分工，也不替代当前团队成员的实际开发交付。

**关系分析**：首次接入时 AST/ts-morph 构图；源码变更后增量重算；缓存命中和失效都要有日志及耗时；DOM 页面实例与源文件/数据保持映射。业务语义候选和明确引用不可混为一谈。  
**范围契约**：候选 ID 与 `ScopeDecision.mode`（如 SHARED / INSTANCE）分离；同一候选要能先共享预演、再仅实例预演、重复验证，避免隐藏的硬编码共享优先级。  
**预演**：文案/媒体/CSS 快速注入与复杂项目隔离修改都可用，但必须测试等效性、基线漂移、应用相同补丁和失败回退。  
**真实证据**：Playwright 抓三视口；对比截图与 DOM 坐标、computed style、交互状态；提供 A 可打开的相对路径或安全图片接口；每条 evidence 绑定 producer、viewport、页面、候选、基线版本、验证状态。  
**外部项目支持**：先在自建青野/栖光实现完整闭环，再对有许可的 React/Vite 开源项目验证“无标记也可识别多少”；无法判断则诚实标不支持/需要适配。  
**可靠性**：覆盖构建、正常视觉差异、确认异常、来源未知、未验证等；无浏览器环境时与 Bolt V6 一样明示“未执行浏览器验证”，不能默默升级成通过。  
**展示评审**：成熟技术的融合、成本/时间、原站点改造最少、用户操作最少与证据可靠性都可以成为亮点，但要以与 Agent 的同任务 A/B 对照数据支撑，而不是只摆技术名词。

### 与分工和现实进度的衔接

由于 B 暂时外出、短期不能用电脑，**可以先使用 Bolt 这类工具生产或补齐演示网站的视觉界面与源码，再把导出的工程作为 Ripple 的被测网站**。但“拿 Bolt 做出好看的青野、栖光站”不等于“完成 B 的分析引擎与预演验证”；两者仍须分别验收。使用工具生成网站很合理：Ripple 的竞争价值本来就不在于替代高质量网站生成器。A 负责 UI/交互整合与代码层适配，C 负责素材制作/查找及授权登记，B 回来后重点对接证据、Scope、第三方验证，项目负责人统筹案例证据与集成验收。此处只是与既有分工相容的可行过渡，不是本轮重新指派工作。

## 10. 下一轮真正需要测什么（对照研究方案）

如果要证明 Ripple 有差异化，应让 Bolt（普通提示与明确要求先分析两种模式）和 Ripple 执行**同一份任务、同一份基线版本**；不要一方给予详细文件提示另一方却不给，从而制造不公平比较。优先选以下对照：

| 任务类型 | 任务指令重点 | 对照观察 |
|---|---|---|
| 共享标题不知情 | “把首页的活动标题改为 X”不提供关系线索 | 谁先告诉用户关联页面；是否误改其他页面 |
| 用户改变范围 | 从共享改为“仅首页”，再撤销范围改回共享 | 是否需要重写提示词；反复修改耗时/错误率 |
| 语义活动更名 | 多处不同写法，历史说明保留 | 找全率、误修改率、语义候选与来源确定性 |
| 媒体裁切 | 横版海报改竖版，多个容器裁切模式不同 | 实际多视口效果、风险检出率、证据定位成本 |
| 非目标负例 | 修改未共享文案、非共享 Token | 是否出现误扩散或虚假影响图 |
| 正常变化负例 | 响应式导航折叠、标题正常换行 | 正常变化是否被误报为异常 |
| 故障/未知 | 断开证据采集、无法定位来源、构建失败 | 是否明确显示“未验证/来源未知” |
| 跨项目接入 | NCDA 与第三方 React/Vite 网站 | 导入/构建/适配/首次构图的成本与成功率 |

**统一记录字段（下轮必须实测，首轮暂缺）**：从输入到首次影响说明的时间；从输入到确认可应用的时间；用户点击数与页面切换数；误改/漏改数量；第一次定位关联内容成功率；三视口实际浏览器覆盖率；来源推断正确率；失败恢复用时；token/付费额度消耗；用户是否能正确说出“哪些已经验证、哪些没有”。每一项同时记录失败和限制，不只留成功截图。

## 11. 阶段判断与决策保留

本轮最显著的事实是：**Bolt 能够做到“共享源码理解 + 局部修改 + 在被要求时先作影响分析”**，而且完成度很好。Ripple 要证明的是另一种编辑决策体验，而不是夸大竞争对手无能。  
同样重要的是：成熟模块的融合创新和成本优化完全可以成为学生竞赛的技术价值。Ripple 应让评委既看懂“尚未落笔，先见涟漪”的完整使用故事，也看见工程上 AST/Runtime、双通路预演、Playwright、证据与补丁一致性是如何协作的。

**当前不立即重写青野/栖光/第三方案例的业务主故事。** 先保留后续讨论方向：青野从“改一个共享标题”扩大为秋季营销活动跨页面更新与范围决策；栖光从单张海报替换转成统一主视觉在不同容器的消费；第三方开源项目以真实 Token 更新验证适配边界。待其他竞品体验完成，再结合真实用户痛点和对照数据收敛案例。

**下一步建议**：将本报告与截图归档、导出 Bolt 站点源码作为独立测试对象；继续“接入已有 GitHub 项目”的真实导入实验以及另一竞品的同任务对照。现阶段不应仅凭本轮体验宣称 Ripple 已经领先。
