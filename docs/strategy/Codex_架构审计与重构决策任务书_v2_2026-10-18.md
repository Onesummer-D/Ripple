# Codex 任务书｜Ripple 架构独立审计与重构方案决策（v2）

**性质**：对现有项目的审计与方案设计。首先只读、不得直接重构仓库或自行删旧文件。  
**基准文档**：[《Ripple 产品定位与架构复审 v2》](./Ripple_产品定位与架构复审_v2_2026-10-18.md)（以下简称 v2）；出现冲突，以 v2 明确决策和真实源码事实为优先。  
**产品中心**：“尚未落笔，先见涟漪”。真实网页修改要连通：原始意图→结构/语义关系→由用户决定范围→可隔离的候选补丁→真实浏览器多状态/多视口证据→同一补丁正式应用→版本及长期覆盖管理。融合成熟技术，不对单项独创性做无意义论证。

## 审计目标：不“保旧”，也不为重写而重写

请逐一给出源码证据（文件+函数/行、关联数据流、当前测试结果、失效场景）：

- Domain 是否真的适合以 Project/EditSession 为中心，而不是把 CaseFixture/CaseId 的几套固定 Demo 硬编码为业务领域？当前 CaseRuntime/ScopeMode/Snapshot 的职责是否正确？
- Static Source Graph 与运行时 DOM 的组件、数据和样式来源能否稳定绑定；Graph node/edge/provenance/confidence 是否能表达结构确定引用 vs 语义候选 vs 历史保护 vs 未知？
- 是否存在针对不同案例写死“3亮1灰”“已通过”、绑定虚构 DOM Anchor 或绕开静态/运行时分析得到的固定 expectedRoutes？
- 现有真实证据来源、截图、视口、测试时间/构建/源码指纹是否与具体 CandidatePatch 一一对应？多次改 Scope/候选/代码变动后是否合理失效；应用的是同一补丁还是重新让 Agent 生成？
- 支持 React 状态、路由、CSS cascade、媒体资产、异步数据、服务端状态的实际难点是什么？目前对任意外部项目接入是否存在可复现路径，还是只能用预设 Fixture？
- B 第二包中的 adapter、分析服务、worktree/快速候选、Playwright 与 A 当前类型契约是否可统一？是否存在编号/路由/节点/截图格式冲突？第三方审计中冻结的开源仓库能否真实启动？
- C 可保留的视觉资产、UI 行为与测试场景有哪些？栖光独立叙事取消后，怎样将 MEDIA 检测迁移青野/通用测试，同时清理冗余 Case？
- 连续更改场景下例外覆盖规则是否易于积累冗余 if/export const；是否能自动找冲突、合并、清理、重新验证并回滚？
- 提示词润色是否可能越权修改用户意图；只读、候选、审批与写入控制是否为明确工作流/工具权限？
- 本地文件、GitHub、ZIP 与 AI 工具导出工程的用户旅程是否可用；接入摩擦、安全隔离与外部环境依赖怎样处理；是否支持未来 IDE 插件的引擎复用？
- 是否过度为展示效果增加复杂 UI、模型调用和截图；动态按风险验证且保持未查项诚实标注的方案是什么？

## 必须提交的可审查交付

### 1. As-is 架构与债务事实表

包含：模块、拥有状态、真实数据来源、依赖图/调用链、覆盖测试、故障复现、长期维护风险，明确分为“真正已跑通”“局部可行”“Fixture/演示”“未验证”“无法满足产品目标”。严禁用“模块已实现”直接替代“用户功能可用”。

### 2. To-be 领域数据模型与状态机

给出用户真实 Project→Session→Intent→Scope/Rule→Patch→Verification→AppliedRevision 的结构化契约、生命周期、不变量、事件、失败与版本漂移；画出模块边界和最少必要的 I/O 接口。说明 TEXT/MEDIA/TOKEN 的统一机制与外部框架映射，不按三个旧 Case 独立建系统。

### 3. 三个**可比较**的架构选项

A 在当前架构基础上修正；B 保留独立可复用模块并重做核心领域与编排；C 从 Project-first 完整重建。分别给：可测试性、扩展适配成本、长期维护、关键不变量、实施工时及迁移风险、需要清除的旧模块和保留的优质资产。**允许推荐 C，不许以既有工作量为唯一理由否决。** 最终应推荐一个方案并列出选择依据及放弃其余方案的真实理由。

### 4. 按用户旅程的端到端验收清单

至少针对同一 Bolt React/Vite 工程：真实接入→运行→指向真实 DOM/源码→共享和语义分析→只改当前/全共享→生成隔离候选→真实浏览器验证→补丁应用→回滚；含“历史保留”“手机布局动画”“旧证据标 stale”“连续多次局部覆盖”“后端 API mock/real 分级”等负例；并对 Lovable TanStack Start 与冻结开源项目明确适配计划和许可证检查。

### 5. B/C 的迁移与团队新分工

逐文件/逐包给出复用、迁移、替代、归档或删除意见。若材料缺失，列具体文件名与需要用户/队员补交的最少必要证据。迁移阶段避免出现两个互相竞争的 graph/Scope/evidence 真相来源。

### 6. 实验计划与性能/用户成本

同一工程同一任务对照原 Agent、Agent Plan+Diff/Preview、Ripple；初次正确率、误改/漏改、总时间、纠错轮次、Token+构建/截图、操作与认知成本、5—10 轮维护规则和误报。Ground Truth 对评审者可见、对受测 Agent 事先不可见；每种方法都可正常澄清，公平比较。

## 判定标准

- **要敢于推翻**不合理的领域/状态/证据组织方式，避免“为修旧架构再造十个 Adapter”。
- **不要以本轮只读审计作为永久功能边界**。目的是给出最优且可实施、可维护、能成长为完整产品的路线。
- 只承认有源码、测试、版本、截图或用户任务验证支持的结果。没有证据的主张做假设；不能把 C 的概念稿当成真实截图，也不能把 B 本地包当已合并 main。
- 不需为比赛预先编脚本或制造错误案例。先让工程通过、产品好用，最后按赛事正式材料规范展示实际成果。

**最终请输出**：审计摘要→as-is 与缺陷等级→三案对比和推荐→to-be 架构/契约→删除与迁移清单→真实端到端验收→B/C 补件清单→具体团队开发与测试安排。**在用户同意推荐架构前，不推送重构代码。**

## 补充审计：Bolt 生成站点作为青野正式视觉基线候选

不能只把 Bolt 当成需要比较的竞品。用户明确认可其生成网站的页面设计，**优先评估直接复用** [ripple-qingye-bolt](https://github.com/Onesummer-D/ripple-qingye-bolt) 中已有四页 React/Vite 工程的业务站点 UI：布局、视觉规范、组件、样式、动态效果、手机响应式，并与 B 包里的青野工程、C 最新资源包、Lovable 的 TanStack Start 工程比较。交付两张清单：（1）青野业务站哪些代码/设计/素材值得直接迁移、哪些因结构、权限、依赖、测试或体验问题必须重构；（2）Ripple 工作台应该学习哪些成熟界面交互，**但不能把青野站点的 UI 当作 Ripple 工作台的 UI**。

核对用户所控制的源码版本和许可：Bolt 的 GitHub 实验工程可能只是初始基线，不可假定 Bolt V2—V6 后续修改已全部在该仓库；逐项检查外部素材与资源许可。重构推荐方案须说明对 Bolt 视觉基线的保留策略，并在真实浏览器中以桌面、平板、手机进行逐页视觉与功能验收，不得为了适配分析引擎而把优质业务站重新做成简陋 Fixture 展示页面。
