## 1. 为什么值得做：问题从“AI 修改代码”升级为“真实作品的修改控制”

用户的目标不是研究组件或图谱，而是：**让网站成为自己真正想要的样子，同时不破坏已经正确的东西**。AI 降低了作品生成门槛，但用户维护既有数字作品时往往仍要承受：意图表达与理解差异、共享/语义关联不透明、变更范围未确认、实际运行结果不可预知、验证结果难以定位或溯源、修正循环及状态回退成本。

Ripple 的中心**不是**抽象的“所有代码变更都会出 Bug”，也不是“跨页面”“裁切”“CSS Token”三个分离需求。这些是可能引发用户困扰的工程机制；真正的连续工作是：

**用户表达或点选 → 系统读取真实工程 → 校准意图并发现关联 → 用户决定应改变与应保留的范围 → 在隔离候选版本中修改/渲染/检查 → 用户看懂变化和证据 → 正式应用经过检查的同一补丁 → 保留可维护的覆盖规则和版本历史。**

无需假设用户的指令必定模糊或 Agent 必定出错。对于完全独立、确定的更改，系统应自然采用简短路径。对于跨共享组件、含历史文本、CSS 覆盖、媒体复用和外部状态的更改，再提升分析深度。**更少的操作和返工，与更强的控制能力，是同一个产品体验的两个面。**

### 1.1 证据支持程度

- **真实用户原话（W）**：[2025-01-22 Reddit r/boltnewbuilders](https://www.reddit.com/r/boltnewbuilders/comments/1i7l1yo/) 用户称，修一个功能时会破坏先前正常的代码或功能；讨论中有用户建议拆分组件、指定不可修改区域，也有人明确表示非开发者很难自行做这种管理。这证明有人遭遇这一类型的困难，不是发生率统计。
- **开发者大样本（W）**：[Stack Overflow 2025 Developer Survey](https://survey.stackoverflow.co/2025/ai) AI 工具困扰题（约 31,476 个回答）中，66% 选择“AI 解决方案差一点就对”，45% 选择“调试 AI 生成代码更耗时”；多选、非 Ripple 样本、非网页改稿专项调查。可论证问题的背景，不可直接估计 Ripple 用户规模与节约比例。
- **可复现工程证据（G/U）**：Bolt 的 B02/B03/B04/B07 与 Lovable 的 L1/L2/L3，验证一个来源跨页复用、独立硬编码文本、页面级覆盖、历史保留及复杂 Agent 能正确修改的多面性。Lovable L3 修改前在 6 个运行文件存在 15 次完整中文名称，数量经 Git 快照复核；这与真实可见的 DOM 实例数不是同一计数口径。
- **技术背景与反例（W）**：[Chromatic TurboSnap](https://www.chromatic.com/docs/turbosnap/) 已用 Git 差异及依赖图选取受影响组件的视觉测试；[WCAG 2.2 文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) 一般正文 AA 最低 4.5:1；[stagewise 官方文档](https://docs.stagewise.io/) 已有本地项目、浏览器选中 DOM、设计预览及 Diff 审查。这些说明已有成熟路线可借鉴，不否定 Ripple 的融合方向。
- **反面场景（H/W）**：有完善 CMS、媒体裁切焦点工具或开发者本来能迅速完成独立文字替换时，完整的多阶段分析可能反而增负。不要把技术潜力包装成已经验证的用户收益。

**证据缺口**：真实目标用户面临此类修改困扰的频率、愿意使用独立工具的比例、对已有 IDE/Agent 的增益、付费意愿、三视口验证能带来的净收益，尚无充分样本。将其转化为可验证实验，而非先写乐观数字。

## 2. 产品定义与目标用户

**定位**：Ripple 是服务于已有网页项目的 AI 辅助**修改决策与可信预演工作台**。用户通过自然语言或真实网页中的点选/直接编辑表达目标；系统将工程来源关系与业务语义联系起来，提供可调整的修改范围和真实浏览器候选，用户决定应用什么，并保留与代码版本一致的可定位证据及后续维护记录。

**愿景**：让非技术用户也能安全、放心地日常维护自己的数字作品；现阶段以网站作为首个具体可落地载体，但架构保持扩展到其他数字作品的可能性。并非定位为新的通用自由创作或通用 AI 网站生成器。

**首批优先研究群体**：拥有或能取得可运行源码，经常借助 AI 修改网站的个人创作者与小团队；典型活动为活动宣传/内容、页面组件与风格、图片更换、商品展示、响应式维护。专业前端开发者既是技术验证对象，也可能在复杂跨组件排查时受益；不能直接假设其付费与日常采用。

**定位警戒线**：用户如果导入项目、启动预览、识别内容来源的成本高于直接编辑，产品主张就失败；不要把“需要更多步骤”误认为“更专业”。Agent、设计工具和浏览器功能可以复用成熟成果，Ripple 关注的是它们对**一次修改决策**的协作方式。

### 2.1 三类用户任务

1. **独立轻改**：改一个不存在共享、无明显风险的文本/图像。应尽量就地处理、快速预览、轻量检查，不让系统为了展示架构而强制用户阅读关系图。
2. **含共享与业务边界的改动**：更新本季活动，涉及多路由、共享配置、历史保护、商品角标、元信息；默认呈现受影响关系及可改范围，支持用户拒绝某些建议。
3. **跨媒介与运行风险的变动**：共享海报换新版本、颜色 Token、动态状态下响应式布局、API 数据造成不同时机的页面表现，按风险启用真实浏览器多状态、多视口验证。

这不是三个产品或三个平行首页，而是同一编辑会话的不同复杂程度与资源类型。

## 3. 统一用户旅程与信息架构

**Project → Source Graph → Edit Session（Intent + Scope）→ Candidate Patch → Runtime/Visual Evidence → Applied Revision** 是领域对象关联，**不是 UI 必须逐页走的死板六步向导**。界面应始终围绕作品画布；其他层渐进展开。

典型旅程：

1. 打开现有源码项目；识别框架/运行/授权/可编辑位置，启动对应的真实网页预览。
2. 用户点选区域、上传新媒体或用语言提出改动；保留**原始表达**。候选目标和保护项由系统从工程读取，标记“确定/推测/未知”。
3. 展示最有用的决策内容：**想改的地方、相关位置、建议保护项、可能的例外与需要确认的问题**；默认摘要，按需展开 AST/DOM 关系、搜索与工程日志。独立修改不强迫展开。
4. 若源共享或语义范围不确定，选择仅当前实例/共享来源/业务相关集合/自定义排除；允许文本、媒体、样式在同一 Edit Session 内形成多项但协调的候选。
5. 在隔离环境生成 **Candidate Patch**，预演桌面/平板/手机和必要交互状态；呈现“预期变化/异常/未检查/证据过期”，支持网页元素↔源码↔证据定位。
6. 用户接受对应候选的范围、变更和证据；系统以**同一 patch+基线指纹**应用、生成分支/PR或输出文件，并在不同的工作区状态中标明“候选／已应用／已提交／已部署”。
7. 后续再次修改时，可查看既存实例覆盖、继承源、历史版本、已失效验证；可合并、撤销或迁移局部覆盖规则，不把多轮修改散落成无法解释的特判。

**原始用户语言不是约束程序的唯一来源**：全局安全/执行策略由工作流实现，不能全押在 Prompt；业务意图不能在“润色”时暗自被模型改写。

## 4. 修改意图校准：自动完善执行方式，而不是篡改用户的需求

研究问题源于 L3：详细“只读、分析、比较方案、等待授权”的约束极大改善 Agent 的人机交互；但这些是**实验者显式提示**的结果，不能自动当作默认平台行为，也不能指望真实用户每次写出繁琐提示词。

采用三层结构：

- **Raw Intent**：保留原话、点选 DOM/页面/当前交互状态、资产操作（如上传新图），不可被改写覆盖。
- **Execution Policy**：Ripple 自动补充**如何工作**：只读阶段不允许写原工程、最小必要读写、标记证据来源、保护无法确定的范围、生成可撤销候选、批准前不应用、测量实际改变。优先由权限与状态机约束，不只是自然语言提示。
- **Intent Hypotheses / Explicit Decisions**：源码与业务语义发现的可能范围、历史保护、媒体替换范围、内容同义候选；主动标注“用户已说/系统建议/需要确认”，只询问对实际结果有影响的问题；用户可以否决。

示例：“本季活动改成秋日手作节，其他别乱动。”系统不应默认把其他所有有关字符串同步改，也不应因为“别乱动”就完全忽略关联。它先提出：本季活动入口与两个宣传页面为结构/语义候选；2023 历史记录建议保护；商品促销角标是否属于本季活动需确认。用户确认后候选才有语义边界。

为减少模型成本：源码索引、图缓存、静态关系和纯确定性匹配优先；只有不确定的业务关联和改动策略调用 LLM；按风险增量扩大验证，但**复用旧证据必须保留版本一致性**。不另起“Prompt 润色”产品菜单。

## 5. 实体/关系建模：源码可证实什么、语义只能建议什么

图谱须区分：

- **Project / Revision / Environment**：真实工程、分支/提交或源指纹、启动环境、依赖锁定与外部服务快照；
- **File / Symbol / Component / Props / Data Source / Media / CSS Token / Route / Rendered Element / Interaction State**：源码节点、浏览器中的消费实例与状态；
- **Edges**：import、renders、reads、passes-prop、uses-token、CSS cascade、data-flow、conditional-render、asset-consumer、route-contains 等确定性或观测性关系；same-text、same-campaign、historical-context 等语义候选要另标；
- **Provenance / Certainty**：静态源码证据、运行时 DOM/样式证据、AI 推断、用户明示、未知；置信度只能与证据范围一致；
- **Positive/Negative set**：将“应该修改的位置”与“用户明确不允许修改的位置”同时作为最终验收依据。

**15 处字面量 ≠ 15 个组件 ≠ 15 个页面实例 ≠ 15 个应修改目标。** 标记“同名”不等于同源；已证明共享引用也不等于业务上应统一更改。L3 中共享 Header/Footer、brandMeta、独立正文、2018 历史条目、SHANYE OBJECTS 和图像中可能嵌入的文字就是一套典型关系对照。

**技术途径**：TS/JS AST/ts-morph 捕获定义和引用，PostCSS/CSS AST + 构建后的 CSS + getComputedStyle 追溯变量、类与级联，浏览器运行时身份/源码映射连接 Route→Component→Slot→Source 与实际 DOM；按框架适配、懒加载和动态数据条件聚焦实际消费。运行时动态构造、反射、第三方库和远程 API 可能无法完整定位时必须保留“来源未知”。

图谱缓存可按 commit、文件 hash、路由、构建配置、依赖树和运行态失效。对源码变更增量分析；不能用早期固定 Fixture Graph 冒充新代码的真实依赖图。

## 6. 范围与长期可维护性：Scope 不是文件勾选，也不是无限特判

一次 ScopeDecision 包含：修改意图、资源/实体、目标页面或组件实例、共享来源、可改集合、保护集合、条件/状态、证据、用户批准版本。至少支持“仅当前实例”“同源所有实例”“若干业务候选”“自定义”概念；具体 UI 可以根据任务隐藏无用选项。

Bolt B03 的 nav 页面判断、B07 的商品 ID 条件、Lovable L2 的 productsPageBadges 映射都说明成熟 Agent 已能实现局部覆盖；但单次成功并不证明长期维护良好。

**覆盖注册与回收机制**：在领域层记录 Rule ID、source/instance、适用条件、优先级、来源用户决策、创建的补丁、最后验证版本、冲突/过期状态。**并不意味着强迫外部站点引入 Ripple 专属运行时**：代码生成器优先选择原项目自然的 props、路由数据、主题配置、数据驱动条件；系统维护独立的可解释规则目录，能扫描实际代码与规则的一致性。

连续更改应检查：同一资源覆盖次数、重复/矛盾条件、孤儿规则、默认源更新是否意外覆盖例外、修改文件扩散、回滚后规则是否正确恢复。系统能提出合并/清理建议，但是否改变既有业务行为仍要用户确认。

## 7. 候选预演：一份可追踪补丁贯穿分析、视觉和应用

**通道 A · 快速预演**：在真实 DOM 上对文本、媒体源、简单样式作短时注入或 overlay，强调实时反馈与低延迟；标明这是“近似草稿”，不能默认等同于完整构建运行的源代码结果。

**通道 B · 完整预演**：用 Git Worktree/隔离工作区或等价文件系统快照生成实际候选补丁，安装与锁定依赖，启动项目及必要服务，构建、执行相关测试、Playwright 浏览器多视口/多状态验证。**这些是真实工程执行步骤，不是只给 iframe 改颜色。**

确认同一性：CandidateID + baseline commit/tree hash + patch hash + build/runtime fingerprint；Scope 或候选值变化产生新候选，旧证明作废或明确声明仅局部可复用；应用前检测主工程漂移，使用已验证补丁而非再次靠自然语言生成新代码。遇到冲突重新预演；支持取消、撤销、历史恢复并测试恢复效果。

“保存草稿”“应用补丁”“Git Commit/PR”“部署上线”是不同状态；绝不能把视觉预演变成线上成功的暗示。需要管理依赖安装、任意脚本执行、文件系统写权限和含敏感信息的环境变量（见 §11）。

## 8. 真实浏览器验证：差异≠异常，Read PNG≠新版通过

统一 Evidence 最低包含：证据 ID、项目/源码基线指纹、candidate ID/patch hash、测试运行 ID、页面 route/URL、视口和像素比、浏览器/环境/构建标识、交互状态、采样时间、测试动作/预期、源码/DOM Anchor、前后截图 URI、computed style/DOM 几何、状态与失败原因、产出器及来源证明。

状态建议：**verified-pass、verified-risk、expected-change、unknown/not-run、stale、failed-to-run、simulation-only**。受影响测试与“未查位置”的覆盖面清楚展示，不把没有运行的检查涂成绿色。

基础视口 1440 / 768 / 375，但布局不是只有三种宽度，需按实际断点或 CSS 容器查询、疑似风险位置补采样。多视口中不要把正常导航折叠、栅格换行、媒体 cover 裁切视作缺陷。Lovable L2 的 IntersectionObserver/Reveal 动画可能造成截图暂时空白；测试应等待字体/图片、滚动触发、稳定动画和预期可交互状态，区分加载态/业务状态/真正丢失。

对图片的裁切，要问关键对象、可读文字和 CTA 是否受到实际影响；有时新 4:5 海报无法在原横向 Hero 中无损显示，应提出布局改变/独立横版素材/局部沿用旧版的可选方案，而不是自称算法必然修好。对 CSS Token，结合浏览器 computed style、Cascade 来源和 WCAG 正文对比度测量，先检测，再解释、再决定改动方案。

参考成熟实践 [Chromatic TurboSnap](https://www.chromatic.com/docs/turbosnap/)：Git 变更与依赖图用于定向选择需重验组件，其他基线按条件复用；并非所有修改一律执行全站三视口重复渲染。选择性验证要能解释“为什么跳过”“原证据对应哪一版”。

可视证据点击链：**历史版本→网页具体变化区域→对应源码与语义/Scope 决策→该版自动或人工验证与时间**。交互第一层显示结论与可选动作，工程第二层展开 Timeline、Diff、工具命令，不要让非技术用户在日志里寻找修改前的决策依据。

## 9. 接入真实项目：来源不应决定用户是否能使用

优先构建**独立可视化工作台 + 可复用分析/预演/验证核心 + 本地运行与仓库连接适配器**，以后按需求进入 VS Code/桌面 IDE/其他 Agent 工作流，避免重新实现全部引擎。插件是一种入口形态而非必须牺牲独立可用性的产品定义。

| 来源 | 理想路径 | 难点、边界与证据状态 |
|---|---|---|
| 本地工程文件夹 | 用户授权→检测项目→工作区隔离→真实开发服务器 | 权限、Node/Python/环境变量、后端服务、跨平台脚本；不是浏览器一拿到文件就能运行 |
| GitHub/Git 远端 | 授权选仓库/分支/Commit→受控克隆→检测→工作分支/PR | 账号权限、私仓、变更冲突与回传；GitHub 非强制 |
| ZIP/AI 建站导出包 | 安全导入→解包检查→依赖恢复→代码分析 | 锁文件、缺失 assets、环境配置、恶意安装脚本 |
| 尚未上线、由 Agent 生成的网站 | 本地源码/导出工程→启动开发预览 | 不要求公网部署，需真实依赖与可运行环境 |
| 仅有 URL、没有源码 | 可以做授权范围内的 DOM/视觉观察和有限建议 | 不能保证能回写真实源码或进行安全提交；不得把抓站当正式工程接入 |
| 服务端/后端项目 | 前后端运行拓扑、隔离数据/模拟服务与真实联调分层 | SSR/API/数据库迁移/鉴权/状态副作用可部分支持；需明确证据是 Mock 还是集成测试 |

**不是“静态网站才能有动画”**。React + TS/Vite 早期作为容易复现的构建基线，响应式动画、状态、筛选购物、API 请求本来就属动态交互。TanStack Start、Next.js、Vue 等由能力驱动适配；针对真实项目逐步建立覆盖矩阵，不把某框架永远排除，也不承诺未测试架构全功能可用。

接入摩擦列入第一等公民：第一次成功加载时间、首次定位可编辑元素时间、失败率、需要用户安装/授权/手改的次数，以及总时间与 Token 费用。若须启动一个第二 IDE 或新增大量账号步骤，必须证明仍有净收益。

## 10. 一段完整自然的用户叙事：青野是综合真实任务，不是功能拼盘

用户已经用 AI 建好并维护“青野文创”网站。运行着活动、商品、历史品牌记录、购物袋和响应式页面。现在运营者说：

> “这次秋季活动更新一下，改叫‘秋日手作节’，新宣传图我准备好了，其他地方尽量不要动。”

此业务请求可能同时涉及文本、图像、样式；**但不能预设每次更新都必然触发三类资源**。实际分析由源码和任务决定。

在产品中，用户无需手写专用 Prompt：编辑区点选/输入需求；系统在**读源码而不修改**时首先报告本季名称和共享来源实际在哪里出现，历史条目与英文品牌是否属于保护项；发现共享宣传图在首页和活动页不同容器消费，提出“同步换图/分别调整/只换其中一处”的方案；现有购物流、商品角标根据用户要求进入回归检查而非偷偷修改。

用户对几项真正有影响的候选范围做决定；看到真实页面里的变更定位、视口/交互状态、未检查项和风险；Agent 按已确认的 Intent+Scope 生成候选补丁；在隔离环境进行真实构建和浏览器验证。若无真实异常，诚实展示通过与未知；若出现遮挡，指出哪一个状态、屏幕区域和构建版本存在问题，并提供可验证的改法。正式应用的是同一候选补丁，旧版与证据可被找回。

**这不是预先写好的比赛台词，也不是规定必须造一个遮挡错误**；它是产品真正需支持的工作过程。复杂任务闭环充分自然，简单编辑就地快捷完成。用户不为了看见“涟漪”而改网站；涟漪只是让他更可靠地得到想要的结果。

## 11. 代码与系统架构：建立可推倒重做的正确边界

建议采用以下**逻辑**模块；不等于必须微服务化：

- **Project Connector / Runtime Manager**：文件夹、Git、ZIP、框架识别、依赖构建、工作区隔离、服务拓扑、能力/权限模型；初始运行态与外部服务 mock/real 的声明。
- **Static Index & Runtime Mapper**：AST、CSS/Token、组件和路由图、身份映射、资源解析、依赖缓存、运行时 DOM/element 与源码 provenance；输出有边界的 Source Graph。
- **Intent & Scope Engine**：原始意图、用户确认的变更集合与保护集合、语义候选、澄清问题、覆盖规则生命周期、跨会话规则管理。
- **Patch Orchestrator**：Agent 接口、受控任务与执行政策、差异和候选分支、previewA/previewB、patch hash、冲突和基线漂移检测。
- **Verification Engine**：build/unit/component/end-to-end/browser multi-viewport, DOM geometry/style, visual diff, performance/time/resource controls, evidence manifest；failure、stale、unknown 等状态机。
- **Revision & Provenance Store**：对齐 Commit/候选补丁/应用版本/证据/用户决策/覆盖规则、差异与恢复。
- **Visual Workbench**：真实作品画布、选中对象、关系涟漪、范围调整、前后对照、证据与历史；主界面只放决策所需信息，开发工具日志按需展开。

**重要隔离**：领域模型不能依赖 React UI，Candidate 与 Evidence 不应直接被当成运行时 Snapshot 的别名，业务项目文件不可当作 Ripple 内部 Fixture 可随意写，插件与 Web 界面不可各建一套逻辑。不要在 JSX、Adapter、分析脚本分别重复计算 source/instance 影响范围。独立纯函数、有类型契约、变更后检测与迁移测试是长期维护基础。

### 11.1 领域对象建议

ProjectRevision {projectId, baselineRef, sourceDigest, runtimeFingerprint}; SourceGraph {nodes, edges, provenance, unresolved}; EditSession {rawIntent, selectedElementRefs, state, decisions}; ScopeDecision {included/excluded, ruleVersion}; CandidatePatch {baseDigest, patchHash, changeset, previewStrategy}; VerificationRun {candidateId, testConfig, startedAt, result}; Evidence {revision/candidate, route, viewport, state, artifact, sourceRefs}; AppliedRevision {appliedPatch, base/targetCommit, evidenceRefs, rollback}; OverrideRule {scope, priority, provenance, lifecycle}。

实体 UUID 或稳定 key 必须能映射到实际项目路径、路由和 DOM 实例，而不是从案例名称拼出。当源码局部改变而身份不稳定时给出迁移、降级或失效策略。可将后端/浏览器与适配器协议契约化，允许未来 IDE 插件复用。

### 11.2 安全与真实性

导入第三方仓库和 ZIP 是在执行未知代码；不能默认把安装脚本、任意网络请求、数据库连接、部署 Token 暴露给 Agent。工作区沙箱、最小权限、敏感环境变量隔离、服务 mock 与可审计回传要成为实现层设计。修改前只读不只是 Prompt；用户批准后的正式修改要记录来源和冲突处理，涉及后端状态时不能误把截图“通过”升级为生产数据库安全。

## 13. 允许重大重构：决定何时保留、何时替换、何时重建

Codex 应做三个可对比的实施方案并给出真实成本而非偏好：

**A 继续现有架构但修正边界**：仅在实体独立、适配协议可复用、patch/evidence 无致命耦合时成立。明确删除多少案例特判、哪些模块不再需要。

**B 保留可独立复用模块、重设计核心领域/工作流**：例如保留 PagePreview、媒体库、测量层、测试工具，重建 Project/EditSession/ScopeRule/Candidate/Evidence/Revision 数据契约。这是**合理的默认待评估方案**，不是预先批准的结论。

**C 以真实工程工作流为中心从零重建**：当现有代码主要服务 Fixture 演示、数据模型根本不支持真实项目隔离与版本一致性，或迁移成本高于重新实现时完全允许。要求明确写出被淘汰模块及保留的资产/证据；历史材料归档不丢。

评判维度：目标场景真实运行通过率、核心不变量可表达性、按框架适配成本、复杂/历史改动鲁棒性、状态与证据一致性、代码内聚/耦合、测试可维护性、安全、长期迭代成本、团队实施风险、既有技术资产迁移。**不按文件数量、修改行数、已完成百分比或“看起来架构高级”决定**。

重构不是无休止的防御性规划：对确定不合理的耦合直接清除，对正确的功能做真实回归；允许大改，但所有关键路径最终要有可运行证据。不以“为了省事先不做”限制产品最终形态，也不以“功能越多越好”强迫无因果关系的模块进入中心。

## 14. 案例组织：一个完整工作与多种真实验收，而非三份故事

### 青野：综合业务工程

真实运营任务承载 TEXT/MEDIA/TOKEN 的**一个编辑会话或持续多次更新**：本季活动改名、共享宣传入口、历史引用保护、素材替换下不同容器效果、必要的样式与可读性检测，保持商品角标和购物功能。项目可复用既有青野资源和 B/竞品工程；不可为了演示“完整技术覆盖”而人为规定每次必有异常。

### 栖光：撤销独立叙事与强耦合 CaseId

C 的海报、容器尺寸素材、媒体库和 B 的 MEDIA 测试都值得留下。将“共享媒体多消费位置、局部/同步覆盖、4:5 与横版不能全部无损兼容、历史 Archive 负例”迁移为**通用 MEDIA 测试集与必要青野任务**；栖光专属故事入口及冗余站点在迁移/验收后可以清理。保留有价值的工程压力用例不等于继续保留另一套业务主故事。

### 第三方：外部项目工程泛化

不再虚构“外部用户一定要改品牌色”的独立商业故事，而是验证：给一个非 Ripple 自建、冻结 Commit 和许可证的真实项目，自动识别组件、CSS 变量/Tailwind 传播、DOM 消费、局部例外与真实视觉结果，生成可应用补丁并留下可验证证据。应选有暗/亮主题、覆盖、路由和动态状态的项目；一个变量从紫色变绿色的动画演示不足以代表泛化。真实项目需提供复现步骤和负例，未识别关系必须可见。

外部项目可以包含 Bolt 导出的 React/Vite 样本、Lovable 的 TanStack Start 样本（访问受限、不要把私有代码公开），再加来源与许可证清楚的开源站进行异构压力测试。对竞赛可公开交付的代码/图片务必符合第三方许可。

## 15. 用户价值评价：只把经过验证的数字写入成果

三组对照**在同一真实工程、同样任务、同样完成判定**下进行：①原 Agent 常规工作流；②成熟 Agent 使用 Plan/Diff/浏览器预览等已有能力；③Ripple 辅助原 Agent（不换更强模型导致混淆）。任务覆盖独立轻改、共享组件局部/全局、历史语义更名、媒体多容器、Token/CSS 覆盖、涉及交互状态的改动，另有连续多轮维护与回滚。

**任务开始前**：参与者单独记录“必须变化、必须保留、可以变化/可选”，形成对研究评审者可见、对 Agent/工具不直接泄漏的 Ground Truth。所有组允许正常的用户提问与澄清；避免给 Ripple 详细提示词而给对照组只给模糊指令。评估者对结果盲评，预先规定可接受的替代实现。

| 维度 | 定义 / 实测方法 |
|---|---|
| 首次候选正确率 | 第一次提交候选中验收项满足数/总验收项；同时报“整条任务全满足率”，不能只报字段平均 |
| 误改 / 漏改 | 应保留而变更的对象数、应修改却遗漏的对象数；按 DOM/页面/业务状态和实际差异归因 |
| 总时间与净收益 | 从导入/表达意图到用户验收完成的全部墙钟时间，含等待、验证、纠错与保存；时间收益率=(对照时间−Ripple时间)/对照时间 |
| 纠错轮次 | 用户追加澄清指令、重新生成补丁及手动回滚/修复次数 |
| 接入摩擦 | 首次可运行预览时间、授权/安装/手动配置次数、接入失败率 |
| 决策摩擦 | 用户理解影响范围所需时间、错误预测数、点击/展开层数、主动确认次数 |
| 计算资源成本 | 模型 token 与实际费用、测试调用/截图数量、浏览器与构建耗时、缓存命中、增量重算 |
| 质量 / 稳定性 | build/test/功能/视觉检验；异常检测 precision/recall、未检查比例、旧证据识别、拒绝非目标修改 |
| 可维护性 | 连续更新 5—10 次后特判/覆盖规则数、冲突/孤儿规则、变更扩散文件数、回滚正确性、后续开发成本 |
| 主观体验 | SUS/SEQ 或 NASA-TLX 等事先指定工具，访谈“理解/控制/信任/打断/是否愿继续使用”，不只问满意度 |

初步可考虑 24—36 名 AI 建站或维护网站的参与者、不同编程基础、组间随机或交叉平衡；这是**招募方案而非已经完成的用户调研**，统计功效应另算。分任务复杂度报告收益；可能出现 Ripple 更准确但耗时更多，仍完整披露。这种结果会指导什么时候轻量、什么时候完整分析。

**实验不仅测系统“分析正确”**：还需测人能不能自然感知、能否做对范围决策以及频繁跨工具切换的真实成本。验证结果要关联测试版本与页面状态，不准从 Fixture 的预置关系图反推系统泛化准确率。

## 16. 成本控制是架构属性，不是新功能入口

根据静态依赖、修改种类、共享实例数量、历史/语义歧义、运行时状态变化、候选 patch 扩散、用户显式保护项与测试覆盖决定验证深度。**这是一种预算与风险决策，不是为了节约 Token 任意跳过安全检查**。

分层计算：源码索引/增量缓存与确定性检查→必要的语义候选 LLM→先定向候选预演→根据真实风险扩大页面/断点/交互状态→复用符合相同源码/环境指纹的旧 Evidence。每项复用留下复用理由和上次版本；当校验无法证明等价时降级为 stale/not-run。

成本不仅是调用模型的钱，也包括用户导入、等待、错误提示、返工、修复上线事故及维护额外覆盖规则的人力。产品成功必须是总体体验和结果的共同改善，不能单用“分析时间缩短”作为结论。

## 17. 成熟方案能直接学习什么：融合与来源披露

- **Bolt**：画布直接选中与编辑、Add changes/Save changes、版本预览；多设备切换；能做局部覆盖和语义改名。其 B07 明确承认本轮没执行浏览器截图，应学习证据诚实。
- **Lovable**：Timeline / Changes / 测试 / Playwright / 图片查看 / 产品角标页级映射；L3 被强提示词要求后能先做深度只读分析、A/B 方案并等授权；L3 改名结果经人工五项验收且 Git 证实 15 字面量和六文件，不能把“强指令行为”说成默认自动发生；截图读取不证明新版绑定 Commit。
- **Cursor / stagewise / Onlook / Builder**：现有工程中的页面元素选择、规划审阅、视觉改稿、嵌入式 IDE/浏览器和 Diff 协作已经有成熟参考；不是需要绕开的竞品障碍，而是可复用的技术和信息组织思路。可实现更多集成而非重复造通用 IDE。
- **Chromatic/Percy/WCAG**：视觉回归、变化影响定向重跑、截图证据管理、无障碍验证可借鉴成熟做法。对于 Ripple 的学生原创贡献，强调数据契约、状态/范围引擎、来源与元素绑定、动态适配、候选与证据一致性的工程整合和交互体验。

不要说“别人没做所以我们独有”，也不要因为别人有成熟模块就自我否定。**学会已有技术、合理接合，形成稳定流畅的解决方案**是产品目标。

## 18. 竞赛材料与实际产品的关系（2026 新规范）

本届《参赛作品材料提交规范》明确：评审视频**建议不超过五分钟**，另有作品展示视频按实际特点调整；视频与汇报 PPT 至少选一项；代表性截图不超过十张；作品/成果文件必交；需真实可运行成果、学生贡献、第三方许可与 AI 使用情况。未实现概念效果不得替代实际结果；材料原则上匿名化。**过去 C 文档“120 秒精华版”只是内部规划，非比赛两分钟硬上限。**

现阶段不先按某个秒数写演示分镜，也不为录制画面制造人工 Bug。先确保真实用户故事、完整系统、证据和评价指标可以成立。产品真正完成后再选择最能反映成果的时长与表达方式。第三方代码/模型/图片/字体/AI 使用须记录来源与许可；最终截图、实际使用说明和工程包均与验证版本一致。

竞赛可论证创新方向（建议根据成品总结为 2—4 项）：①结构确定关系与业务语义候选的可操作范围决策；②实际 DOM 关联的跨资源/视口视觉预演与 Evidence；③候选补丁、用户批准、应用版本的一致性与长期覆盖管理；④真实外部项目接入的可复验系统集成。最终表述根据交付事实再调整，不能事先以概念图声称已经实现。

## 19. 综合验收门槛：什么叫“完整实现”，什么叫“仍需整改”

核心产品验收应至少具备：从真实非预设源码导入并运行 → 用户自然编辑 → 实际解析 Source Graph/Runtime 元素 → 保留用户意图和保护范围 → 多候选 Scope/局部覆盖 → 生成可审阅候选补丁 → 在真实隔离环境可运行预演 → 视觉/DOM/功能验证且有版本绑定 → 用户确认同一 Patch 应用 → Git/文件交付、回滚与连续再次维护。一处步骤仅靠 Fixture、人工硬编码或本地未接入的素材示意，不能称这条端到端真实工程能力已经通过。

主工程每次重构必须提供：验收源 Commit、冻结的第三方样本及许可、跨框架对照、失败/边界用例、候选和 Evidence 版本一致性检查、适配耗时、代表性源码 Diff、测试及浏览器日志、团队贡献记录。

测试应覆盖**正常成功、错误和未知三种条件**：不共享时无需复杂提示；共享变更可正确同步或局部例外；历史文本保留；图片裁切无法自动解决时诚实反馈；CSS token 暗/亮主题与覆盖；未启动后端仅 mock 的状态；旧截图/旧代码证据降级；隔离应用失败不污染原工程；撤销及恢复真实成立。

## 20. 后续产品形态与发展空间

核心引擎须 API/CLI 可复用，前端工作台只渲染统一的 Edit Session。发展方向可包括：本地应用/桌面工作区、VS Code/IDE 插件、与其他 AI 编程工具协同的审批与验证层、多人审查与审计、其他数字作品类型；这些是架构可扩展方向，不是本轮已建成或保证能商业化的陈述。

**更有价值的未来路径不是复制已有 Agent**，而是让现有 Agent 或团队已经生成的修改作为 Candidate 输入 Ripple：它读取真实 patch，解释影响、允许缩改范围、做视觉验证，再将批准结果回传。这样既支持用户从 Ripple 发起编辑，也支持 Agent 在别处改稿后进入 Ripple 复核。对开发者自然融入现有工具，对非开发者保留独立可视界面。

## 21. 需 Codex 给出的正式审计结论及团队协作安排

在实施前进行**只读技术审计**：冻结 Ripple main Commit；枚举真实能力与 Fixture 占位；对照上述真实会话生命周期；读取 B 的 10-14 第二包并实跑（在隔离环境）；读取 C 的视觉稿并标明概念/可复用资产；核对现有 A 的测试证据及适配器契约；给 A（保留调整）、B（核心领域重构）、C（全量重建）三套方案的工程成本、风险和可维护性评分，并推荐一套，不回避推翻重写的选项。

选定路线后再给出具体架构图、目录/契约迁移、遗留代码删除清单、真实工程闭环验收矩阵、团队 A/B/C 改进后职责、素材迁移、连续迭代及测试策略。**没有独立审计结论前不能直接以现有 CaseFixture 为中心继续扩展多个新功能**；同时已有通过的 A 本地功能不能凭口号直接视为无价值。

**团队事实检查**：B 包不等于已提交主仓库；C 10-12 包不一定是最新；A 主仓库验收只说明特定构建；第三方实际站点未冻结/运行前不能宣称泛化已验证。这些状态在审计报告里必须逐项标注，并让团队提供缺失的最新交付包/证据。
